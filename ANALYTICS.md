# Аналитика расходов

Аналитика использует только внесённые расходы. Внутри выбранного периода дни без операций равны нулю; подтверждения дня нет. Для обучения прогноза и поиска закономерностей даты до первой операции исключаются. День определяется по серверу в `Asia/Yekaterinburg`, будущие расходы запрещены в обеих формах и API. Будущие бюджеты разрешены.

## Интерфейс и расчёты

Единый раздел «Аналитика» доступен на телефоне и компьютере. Общий фильтр категории управляет показателями, динамикой, календарём, привычками и аномалиями. Круговая диаграмма сохраняет все категории, выделяя выбранную. Операции дня, привычки и отклонения доступны для просмотра и существующих действий над расходами. Быстрый ввод остаётся доступным из любого раздела.

`web/analytics-core.js` содержит чистые расчёты; `web/analytics-view.js` — отрисовку. Расчётные функции принимают дату явно. История загружается существующим API, отдельного аналитического backend и внешних нейросетей нет.

- Сравнения недель используют понедельник–воскресенье, прогноз — существующие бюджетные недели, ограниченные месяцем. Текущий месяц сравнивается с тем же доступным числом дней предыдущего; завершённые месяцы — целиком. Полная сумма выбранного периода показывается отдельно от суммы сопоставимого диапазона. Произвольный диапазон сравнивается с предшествующим диапазоном той же длины. Среднее и медиана включают нулевые дни; нулевая база не даёт процент роста.
- Прогноз использует восемь недель до начала бюджетной недели. Если для всех оставшихся дней недели есть хотя бы четыре наблюдения, смешивает историческое среднее соответствующего дня недели и текущий темп с весом `n / (n + 3)`. Иначе требуется минимум два завершённых дня текущей недели. Сегодня оценивается не ниже уже внесённой суммы. Остаток считается относительно актуального лимита. Для закрытых/прошедших недель остаётся факт.
- Привычка — минимум три операции на трёх датах с одинаковой категорией и нормализованным описанием. Оригинал описания сохраняется. Экстраполяция возможна от 28 дней наблюдаемого периода, месячный коэффициент — 30,4375 дня, годовой — 365,25. Сравнение привычек использует предыдущий равный по длине диапазон. Справочник магазинов разрабатывается независимо; его будущая интеграция не требует переписывания описаний.
- Аномалии используют до 12 предшествующих недель и минимум восемь сопоставимых наблюдений: тот же день недели для дня, завершённые недели для недель и категорий. Порог — выше `Q3 + 1,5 × IQR`, рост не меньше 50%, разница с медианой от 500 ₽ для дня/категории и 1 500 ₽ для недели. Нулевая медиана обозначает появление расходов, без утверждения об аномалии. Сегодня может быть отмечен как высокий расход, хотя день ещё не завершён.
- Симулятор использует завершённый месяц. Для пересекающихся сценариев к каждой операции применяется наибольшая доля сокращения, без двойного счёта. Фиксированная сумма распределяется пропорционально операциям группы. Годовая экономия — месячная × 12. Сценарии живут только в интерфейсе и не меняют факты или бюджеты.
- Месячный отчёт всегда строится из актуальных операций. Текущий месяц помечается промежуточным. Показатели, категории, изменения, привычки и отклонения используют общий модуль.

API добавляет `today` (`YYYY-MM-DD`) и `timeZone` в успешные ответы. Интерфейс сверяет дату при возврате в приложение и раз в минуту. Валидация на сервере остаётся обязательной; пакет с будущей датой отклоняется атомарно.

## Удаление переносов между месяцами

Миграция `0005_remove_month_transfers.sql` удаляет `months.incoming/outgoing`. Бюджетом становится исходный `budget`; ненулевые переносы отменяются с перераспределением открытых недель существующим алгоритмом. Если все недели закрыты, последняя хранит остаточный лимит. Нулевая история переносов не меняет ни одну неделю. Несовместимость с закрытыми лимитами прерывает всю миграцию. Расходы, аккаунты, ревизии и квитанции запросов сохраняются. Межнедельные переносы и `settled` остаются.

Локальный сервер обновляет схему при запуске, создавая файловую резервную копию перед миграцией 0005. Тесты используют отдельные базы.

Облачный выпуск требует следующего порядка:

1. Выполнить тесты и `npx wrangler deploy --dry-run`.
2. Включить обслуживание: `npx wrangler deploy --var FINANCE_MAINTENANCE:1`. Оно блокирует API, включая вход и записи.
3. Экспортировать D1 в игнорируемую папку: `npx wrangler d1 export finance-tracker --remote --output data/backups/before-analytics.sql` (для каждого выпуска использовать новое имя).
4. Проверить экспорт и репетицию: `python tools/verify_analytics_migration.py data/backups/before-analytics.sql`.
5. Применить миграции: `npx wrangler d1 migrations apply finance-tracker --remote`.
6. Экспортировать результат в отдельный SQL и проверить `python tools/verify_analytics_migration.py BEFORE.sql --after AFTER.sql`. Проверяется точное совпадение операций, аккаунтов, ревизий, квитанций и ожидаемой финансовой модели.
7. Опубликовать обычным `npx wrangler deploy`, снимая обслуживание. Проверить HTTP, соответствие статических файлов, `today/timeZone` и закрытый доступ к `/api/state` без сессии.

Старый Worker несовместим со схемой после миграции. При ошибке проверки обслуживание остаётся включённым; исправление выполняется до открытия API. Восстановление из резервной копии требует согласованного восстановления старой схемы и версии Worker, а не одиночного отката кода.

## Проверки

`npm test`, `npm run test:analytics`, `npm run test:parity`, `npm run test:edge`, `npm run test:client`, `npm run test:parser`, `npm run test:categories`, `npm run test:browser`, `npm run test:analytics-browser`, `npm run format:check`.

Worker проверяется на отдельной локальной D1: миграции и `wrangler dev --local` с одинаковым `--persist-to`, затем `TEST_WORKER_URL=http://127.0.0.1:PORT npm run test:worker`. Тесты Worker отказываются работать с production. Браузерные тесты сохраняют снимки в `data/`, проверяют ширины 320/390/1440 px и не используют пользовательские операции. Настоящие iOS/Android требуют отдельной проверки.
