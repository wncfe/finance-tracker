# Нормализованное хранение бюджета

Миграция 0003 и новый Worker опубликованы в production 7 ноября 2026 года. Перед миграцией запись была остановлена, сделан свежий экспорт. Экспорт после миграции подтвердил полное совпадение финансовой истории, аккаунтов, ревизий, сессий и квитанций. Контрольные копии и отчёт находятся в `data/backups/release-*` и `data/backups/production-normalization-verified.json`, вне Git.

Источником финансовых данных стали таблицы `months`, `weeks`, `expenses` и `categories`. Расход имеет собственную строку, прежний ID и внешний ключ категории; категория имеет стабильный ID и отдельно название. Составные внешние ключи связывают расход с неделей и аккаунтом. Индексы поддерживают выборки по месяцу, дате и категории. Суммы остаются целыми копейками. `operations` продолжает хранить квитанции запросов.

`users.state` удаляется миграцией после переноса. Репозитории `finance_store.py` и `cloudflare/finance-store.mjs` собирают прежний формат `state` только в памяти для API и проверенного расчётного движка. Изменение расхода записывает изменённые строки, а не весь документ; для добавления в существующую неделю достаточно одной финансовой записи. Существующие недели, ID расходов, порядок, категории и описания не пересоздаются.

Транзакция объединяет финансовые строки, ревизию и квитанцию. В D1 условные записи защищены уникальным токеном конкретной транзакции: при проигранном CAS ни квитанция, ни расходы не записываются. Глобальная ревизия аккаунта пока сохранена, поскольку расчёты и переносы затрагивают несколько недель и месяцев. Чтение всего бюджета в API также пока сохранено. Для очень большой истории следующий этап — постраничное чтение и отдельные версии агрегатов; текущая работа устраняет документное хранение, но не обещает неограниченную масштабируемость.

## Резервирование и локальная проверка

SQL-экспорт облачной D1, восстановленная исходная SQLite и манифест находятся в `data/backups/`. Исходные файлы не перезаписываются. Нормализованная рабочая копия — `data/normalized-real.sqlite3`; подробный отчёт — `data/normalized-real.verification.json`. Все эти файлы исключены из Git.

`tools/audit_backup.py` восстанавливает экспорт в новый файл, проверяет целостность и записывает SHA-256. `tools/verify_normalization.py` открывает исходную SQLite только для чтения, создаёт новую копию, выполняет миграцию и сравнивает весь финансовый документ каждого аккаунта. Дополнительно сравниваются учётные данные, ревизии, сессии, ограничения входа и квитанции. Исходные расходы не используются как тестовые записи для изменений.

Проверка текущего снимка: 2 аккаунта, 1 месяц, 6 недель, 32 расхода, 2 076 009 копеек. Содержимое финансовых документов до и после идентично. SHA-256 канонического представления до и после: `cd50f35536fb28b53cc6a1b6e2e04956665ad8c869ab573b9fc253ae598db2fa`.

Локальная Python-миграция сравнивает весь документ до коммита и откатывает схему при различиях. SQL-миграция отказывается молча отбрасывать неизвестные поля, проверяет количество перенесённых сущностей и ограничения связей. Старые нестандартные категории сохраняются отдельными записями справочника.

Проверки: `npm test`, `npm run test:browser`, `npm run test:worker` с отдельной локальной D1, `npm run cf:check`. Дополнительные тесты покрывают `settled`, старые категории, порядок расходов, повтор миграции, откат схемы при неподдерживаемых полях, внешние ключи, отсутствие перезаписи неизменённых расходов и реальный облачный снимок, если он доступен локально.

## Будущий перенос production

Перед публикацией нужен свежий экспорт, остановка записи на период переключения и повторное сравнение на свежем снимке. Миграция удаляет старое поле, поэтому старый Worker и новая схема несовместимы: нельзя запускать обновление миграции отдельно на работающем старом приложении. Необходимо согласованное окно переключения, проверка после миграции и готовый план восстановления из свежего экспорта. Бэкап текущего исследования не заменяет свежий бэкап перед фактическим переключением.

Персональные правила быстрого ввода остаются в браузере: их не было в облачной базе и переносить из неё нечего. Синхронизация этих правил между устройствами — отдельное изменение.
